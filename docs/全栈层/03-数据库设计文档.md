|---|---|---|---|---|---|---|---|---|
| id | TEXT(36) | 是 | — | ✓ | — | PK | 任务唯一标识，UUID4（`new_task_id()`） | — |
| user_id | TEXT | 是 | — | — | — | idx_user | 提交者标识；当前无认证体系，API 默认 `"local"` | — |

## 3. 状态机约束（应用层强制）

DDL 层不做 CHECK 约束，流转由 `server/state.py::TRANSITIONS` 强制：

```
PENDING ──► RUNNING ──► SUCCESS
   │           │──► FAILED
   │           │──► TIMEOUT
   └──────────►│──► CANCELLED（软取消）
   （PENDING 也可直接 → CANCELLED）
```

- 终态：SUCCESS / FAILED / CANCELLED / TIMEOUT（finished_at 非空）
- 越态写入视为程序 bug（第二步 SQLAlchemy 升级时考虑加应用层断言）

## 4. 索引设计

| 索引名 | 定义 | 依据 |
|---|---|---|
| `PRIMARY` | (id) | 主键点查：GET /render/{id} 全部路由走此索引 |
| `idx_state_created` | (state, created_at) | 运维查询「进行中任务」`WHERE state IN ('pending','running') ORDER BY created_at`；僵尸任务扫描 |
| `idx_user` | (user_id) | 按用户查历史任务（第四步多用户/回调统计前置） |

> 说明：第一步 sqlite3 DDL 仅含 PRIMARY KEY，**两个二级索引在第二步 SQLAlchemy 升级时一并补建**（对现有 API 零影响，属加法迁移）。

## 5. 访问模式与并发策略

| 访问方 | 模式 | 策略 |
|---|---|---|
| API 层 | 点查 get / 创建 / cancel 更新 | 每次操作独立连接 + `timeout=10s` |
| Worker（Celery） | 状态推进 update + 检查点查询 | 同上；SQLite 文件锁覆盖「1 worker + API 线程」写竞争 |
| 取消可见性（拍板） | worker 四个检查点查 `state` | **DB 查询态**：`state=CANCELLED` 本身即标志位，无独立 flag 表 |

**第二步 SQLAlchemy 升级要点**：连接管理改为 engine + session（保持 per-operation 短事务）；字段名/表名不变，现有 5 条 API 测试作为回归护栏。

## 6. 数据保留与清理

- `result_url` 指向的成片：本地 FS 存储，临时目录用后即清；正式产物 TTL 清理随第四步 MinIO 迁移统一定义
- 任务记录本身：不清理（SQLite 单文件，量级可承受）；第四步引入 `task_events` 审计表时再定归档策略
